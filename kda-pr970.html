01 / FIRST LOCATE THE OPERATOR

这里实现的不只是那一条递推公式

mega_recurrent_kda_replayssm 的 README 把它定义为 Kimi K3 ReplaySSM 的 verify（验证候选 token）片段。它把输入投影、短卷积、KDA 状态更新和输出投影合在一次 mixed AIC/AIV kernel 调用里。这说明此算子的用途，不等于本页核实了整个 Kimi K3 的模型结构。

M1 · 从 X 投影出 Q/K/V 和门控输入→ M2 · 因果卷积 + SiLU + Q/K 归一化→ M3 · 衰减 + 纠错 + 读取 + 输出门控→ M4 · 输出投影

“投影”就是输入向量乘训练好的权重，产生不同用途的向量。Q 用来读取记忆，K 表示写入位置，V 表示希望存入的内容。因果卷积在这里看当前位置及之前 3 个位置；Q/K 再除以各自长度（带稳定项），得到接近单位长度的向量。

本版固定候选长度 8、隐藏维度 7168、每头维度 128；支持本地头数 6/12/24 和受整除条件限制的 batch。它是特定短序列的递推融合实现，不能把其测量结果直接当成长序列 prefill 的 chunk 算法结果。

“线性 Attention 的 φ”在这份代码哪里？

基础课中 φ 是把 Q/K 映射为特征的函数，用于解释怎样把历史 KV 累加成一个状态。这份实现的 golden 直接对卷积后的 Q/K 做 L2 归一化，再进入 Delta 递推，没有课上玩具例子里的 φ(x)=x+1，也没有线性 Attention 中的归一化累计量 z。

两者的关联是“用固定大小的状态保存历史信息”。KDA 在这个思路上引入遗忘和误差纠正，具体更新公式已经改变，不能原样套用基础线性 Attention 的分母。

02 / SAME MEMORY, DIFFERENT STORAGE

为什么代码里 D 写在状态右边？

课上用 S 表示记忆矩阵，行对应 key 通道，列对应 value 通道。此代码按相反方向存储。为避免混用，本页用 M=Sᵀ 表示代码中的状态：行是 value，列是 key。ᵀ 表示交换行与列。

课上：S̄ = D S旧；　v̂ = S̄ᵀ k；　S新 = S̄ + k uᵀ
代码：M̄ = M旧 D；　v̂ = M̄ k；　M新 = M̄ + u kᵀ
其中 u = β(v − v̂)，　o = scale · M新 q

D 是对角矩阵，对角线存放各 key 通道的保留率 α。左右位置变化来自转置，仍然是先衰减，再用衰减后的状态预测 V。v̂ 是“当前记忆沿 K 读出来的内容”，不表示预测下一个 token。o 才是沿 Q 读出的本步输出，之后还要做输出处理。

展开：拿同一组 2×2 数字核对两种写法
课上 S旧 = [[10, 20], [30, 40]]
代码 M旧 = [[10, 30], [20, 40]] = S旧ᵀ
α = [0.9, 0.5]，D = [[0.9, 0], [0, 0.5]]

S̄ = D S旧 = [[9, 18], [15, 20]]
M̄ = M旧 D = [[9, 15], [18, 20]] = S̄ᵀ

k = [1, 0]，v = [100, 200]，β = 0.5
v̂ = M̄ k = [9, 18]
u = 0.5 × ([100,200] − [9,18]) = [45.5,91]
M新 = M̄ + u kᵀ = [[54.5,15], [109,20]]
S新 = M新ᵀ = [[54.5,109], [15,20]]

两种写法给出完全相同的记忆，只是摆放方向不同。真实实现里两个维度恰好都是 128，仅看形状看不出区别，要看乘法的求和方向。

03 / THE ACTUAL CHANGE IN PR970

β 不是投影出来就能直接用

投影先给出一个任意实数 ℓ（logit），再通过 sigmoid 把它变成 0 到 1 之间的纠错系数。logit 在这里是激活前的数值，不要求你先把它理解成概率。

ℓ = X Wβᵀ；　β = sigmoid(ℓ) = 1 / (1 + exp(−ℓ))
u = β(v − M̄k)

exp(x) 就是 e 的 x 次方。β 小，修正少一点；β 大，修正多一点。若 K 是单位长度，沿同一个 K 读出的新预测为「旧预测 + β×误差」。

教学标量例子，用来放大机制区别，不是 PR 测试输入。

例如 ℓ=0 时，正确 β=0.5，新预测=0.4+0.5×0.6=0.7；若直接拿 ℓ 当 β，会变成完全不纠错。ℓ 为负时还可能朝相反方向修改。

此次 PR 补的是默认双 token 路径 rec_pair_vf 中漏掉的 sigmoid。单 token 路径 rec_token_vf2 和 CPU golden 原本已有这一步。双 token 融合、流水和预取是该版本已有设计，不是此次补丁新加的性能优化。

展开：补丁里的向量指令对应什么？
bl = full(beta_logit)  → 把标量广播到向量各 lane
nb = neg(bl)          → −ℓ
eb = exp(nb)          → exp(−ℓ)
db = adds(eb, 1.0)    → 1 + exp(−ℓ)
b  = div(one, db)     → 1 / (1 + exp(−ℓ))

这是指令含义的简写，两个 token 分别执行。变量名 beta0/beta1 本身不能证明值已激活，要追溯调用者传来的是 ws_beta_logit。

04 / WHERE THE FORGETTING RATE COMES FROM

α 也来自输入，而且每个通道不同

本页把真正的保留率统一叫 α；源码工作区常叫 decay。它是每个 token、每个 head、每个 key 通道各一个数。设 r 是两段投影产生的 raw_decay，b 是训练得到的 dt_bias，a 是 a_log，L 是非正的 lower_bound：

x = exp(a) · (r + b)
g = L · sigmoid(x)
α = exp(g)

先把 x 压到 0～1，再乘负数 L，得到非正的对数保留率 g；最后 exp(g) 得到 0～1 的保留率 α。若 L=−5，数学上 α 在 e⁻⁵ 和 1 之间；浮点计算可能取到边界。注意 L=−5 是对数保留率的下界，α 的下界约为 0.00674。

x=0 时 sigmoid=0.5，所以 g=−2.5，α≈0.0821；一份旧记忆单步只剩约 8.21%。x 越大，α 越小，遗忘越强。源码 decay_vf 的形参 alpha 实际装的是 exp(a_log)，不是这里最终的 α，读代码时尤其要区分。

展开：和之前的 αᵗ、半衰期有什么联系？

若同一通道每步 α 都相同，而且不写入新内容，旧记忆经过 T 步剩 αᵀ 倍。这里 T 是步数，αᵀ 在这句话中表示幂，不是矩阵转置。

若每步不同，就变成 α₁×α₂×…×αₜ = exp(g₁+g₂+…+gₜ)。这描述一份旧内容的直接衰减因子；完整 KDA 还包含纠错写入，不能用这一个乘积替代整个状态递推。

固定 0<α<1 时，半衰期为 ln(0.5)/ln(α)。若 α=1 则不衰减，不能代入分母为 0 的公式。

量维度与作用与另外两个的区别
α / decay每 head 每 key 通道；先遗忘决定旧记忆保留多少
β每 head 一个数；乘纠错量决定本次误差修正多少
sigmoid(gate)每 head 每输出通道；在 RMSNorm 后使用控制读出的结果传出去多少，不直接修改状态

05 / FUSE TWO STEPS WITHOUT LOSING DEPENDENCE

两个 token 一起算，第二个还依赖第一个吗？

依赖。不能都从初始状态独立预测。优化把第一步对第二步的影响显式展开，以减少反复扫描大状态。以下 0、1 表示一对中的先后两个 token，M 是这一对开始前的状态。

u₀ = β₀(v₀ − M D₀ k₀)
M₀ = M D₀ + u₀ k₀ᵀ
u₁ = β₁[v₁ − M D₀D₁ k₁ − u₀(k₀ᵀD₁k₁)]
M₁ = M D₀D₁ + u₀k₀ᵀD₁ + u₁k₁ᵀ

第三行来自把第二行代入 β₁(v₁−M₀D₁k₁)。括号里的 k₀ᵀD₁k₁ 是一个数：第一步写入的地址，经过第二步遗忘后，与第二个地址有多少重合。乘上 u₀，就是第一步对第二次预测的贡献。它对应源码中的 sk / skv，不能漏掉。

展开：用只有一个通道的数字逐步验算
初始 M=0.4；k₀=k₁=1；两个目标 v₀=v₁=1
α₀=α₁=0.9；β₀=β₁=0.5

第一步：先衰减 0.4×0.9=0.36
u₀ = 0.5×(1−0.36)=0.32
M₀ = 0.36+0.32=0.68

第二步：先衰减 0.68×0.9=0.612
u₁ = 0.5×(1−0.612)=0.194
M₁ = 0.612+0.194=0.806

展开后：M D₀D₁ = 0.4×0.9×0.9=0.324
第一步写入留下的影响 = u₀×0.9=0.288
第二次预测 = 0.324+0.288=0.612
最终状态 = 0.324+0.288+0.194=0.806

如果漏掉第一步的影响，第二次预测会错算为 0.324。两步融合保留的正是这份依赖。

读取同样可以展开：o₀/scale = MD₀q₀ + u₀(k₀ᵀq₀)，o₁/scale = MD₀D₁q₁ + u₀(k₀ᵀD₁q₁) + u₁(k₁ᵀq₁)。代码先预计算这些小向量的点积，再扫描状态算两步共用的项。

一个 128×128 的 FP32 状态有 64 KiB，而一个 128 维 FP32 向量只有 512 字节。共享状态扫描很有价值。这里的优化包括片上 UB 与寄存器之间的数据访问；不能把每一次状态 load 都称为访问 HBM。

在精确实数运算下两种写法等价。浮点求和顺序不同，需要按容差验证；仅凭公式等价不能推断逐位相同。

06 / SAVE THE UPDATE, NOT EVERY FULL STATE

replay_u / replay_k / replay_decay 保存什么？

每一个候选 token 的状态更新，只需要旧状态加上三类数据就能描述：

M新 = M旧 · Diag(replay_decay) + replay_u · replay_kᵀ

replay_u 是已经乘过 β 的纠错向量 u；replay_k 是归一化后的 K；replay_decay 是逐通道保留率。这些记录可以用来重放更新，而不必为每个候选都保存完整的 128×128 状态快照。

本算子内部依次更新临时状态计算 8 个候选，但接口中的 recurrent_state 是只读初态，不会自动写回第 8 步状态。返回最终输出，并原地写出 replay 记录及更新卷积缓存。候选接受与后续状态提交由算子之外的流程处理，本次 PR 没有实现完整的接受协议。

展开：为什么能省存储？重放能逐位恢复吗？

每 head 每 token 的完整 FP32 状态是 128×128×4=65536 字节；u 和 K 各用 FP16，decay 用 FP32，合计 128×(2+2+4)=1024 字节，是这两类记录大小的 1/64。这个比值只比较单步记录，不包括初态、卷积缓存、工作区等总开销。

核心递推使用 FP32，但 replay_u / replay_k 写出为 FP16。因此重放是压缩记录下的数值恢复，不能据此承诺与内部 FP32 临时状态逐位一致。

07 / WHAT THE OPTIMISATIONS ACTUALLY SAVE

从“少算几次”到“少等、少搬”

代码里的手段为什么有用要付出的代价
一个 mixed kernelCube 做投影矩阵乘；Vector 做卷积、归一化与递推，减少多次起核仍有 ws_qkv / ws_gated 等工作区，并非中间量全在片上
M1→M2 面板双缓冲一块投影结果准备好就让 Vector 消费，Cube 继续做后续面板槽位复用前必须确认消费者读完，防止覆盖
M3→M4 按 slot 发布已完成的 head 先进入输出投影，让下一批递推与当前投影重叠发布过细会增加握手成本，过粗又让 Cube 等待
跨 item 预取提前加载下一个 (batch, head) 的数据，尝试隐藏搬运延迟占用更多 buffer，并非每种小核数/几何配置都合算
rec_pair_vf 两步融合共享状态扫描，预计算点积来保留两步因果依赖展开项和寄存器更多；每条路径都必须保留 sigmoid 等语义
N384 / N128 面板、m-tile 阶梯与 split-K根据任务规模调整分块；小任务也能分给更多核小块有调度成本；split-K 的 BF16 atomic 累加顺序可能变化

读源码时可按 GeometryKey → _module1_cube / _module2_vector → _m3_loop_prefetch → rec_pair_vf → _module4_cube 的顺序。先识别数据依赖，再研究 READY / RELEASE、PUB_VEC / PUB_ACK 等事件。

和 PyPTO 的比较，能从这份 PR 得出什么？

此文件明确导入 pypto_pro.language，通过 pl.vector_function、vf.*、显式 buffer、搬运和核间事件实现上述设计。PR 没有提供同一算子的普通 PyPTO 对照实现与同口径计时，不能据此计算“Pro 比 PyPTO 快几倍”。

做有效对比需要固定数学契约、输入形状、dtype 舍入边界、初始状态和硬件环境，再比较拆分实现与融合实现的耗时、访存和核利用率。语言名字本身不是性能证据。

08 / A PASSING TEST CAN STILL MISS A FORMULA ERROR

性能数字要连着计时口径读

RESULTS 的 48 点来自 Ascend 950DT、CANN 9.2.0，采用 msprof --task-time；每点 3 次预热、20 次采样取算术均值，每点独立进程，每次恢复卷积状态，并读 224 MiB 缓冲驱逐 L2。

例如 N=6、B=16：8 AIC 为 154.6 μs，32 AIC 为 69.4 μs。这是同一作者报告中不同起核数的比较，不能当作此次 sigmoid 修复带来的加速，也不是包含 host 校验和工作区分配的端到端调用延迟。

作者报告补 sigmoid 后 48 点耗时变化不超过 1.5%。可以读出“此次修复在该测试范围内没有明显性能回退”，不能推导出所有形状都一样。README 和 RESULTS 的软件版本表存在差异，复现时应以实际记录的环境为准。
